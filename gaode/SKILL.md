# 周边去哪儿

完成一次“理解需求 → 高德地点搜索 → 高德步行路线 → 筛选推荐”。输出简洁、可核对的地点备选，让用户知道去哪儿以及从起点步行需要多久。每个地点均从同一起点独立出发，不串成多站行程。

## 1. 提取需求

从输入确定：城市、起点经纬度、地点类型或关键词、步行时间上限、推荐数量、硬性条件及排序偏好。

- 起点使用用户或平台明确提供的坐标；按工具声明的经纬度顺序传参。高德常用 `经度,纬度`，不可颠倒或擅自改为附近地铁站、商圈中心。已给坐标时无需设备定位或 IP 定位。
- 未指定数量时最多推荐 3 个；指定数量时取该数量与 3 的较小值。不得为凑数重复同一地点。
- 将时间上限统一为秒，例如 15 分钟为 900 秒；用户未设上限时不自行加上“15 分钟内”等硬限制。“以内／不超过”包含边界，“少于”不包含边界。
- 区分“必须／只要”等硬条件和“优先／尽量”等软偏好。例如“优先近一点”影响排序，“步行不超过 15 分钟”决定是否入选。
- 评测输入已含明确起点，直接执行。其他使用场景确实缺少定位必需信息时，再简短询问城市和起点坐标；不猜测坐标。

## 2. 查询真实候选地点

先查看当前高德 MCP 可用工具及参数 schema，选择地点搜索和步行路线规划能力。工具名称、必填参数、可用分页、单位和返回结构以运行环境为准，不编造工具或参数，也不要求用户提供 API Key。

优先调用**周边搜索**：中心点为原始起点，关键词对应用户要求的地点类型。若提供类型过滤、距离排序、城市或半径参数，按 schema 使用。类别词要能命中实际 POI，例如“咖啡馆／咖啡厅”；不要把整句需求当成唯一搜索词。

- 首轮取得多于目标推荐数的候选，通常 6–10 个即可；工具返回更少时使用实际结果。搜索半径仅用于收集候选，不能证明步行可达。
- 未指定搜索范围时，可从约 1000 米半径开始；必要时结合时间上限调整或扩大一轮。不要把经验半径或直线距离换算为步行耗时。
- 若只有关键词搜索，结合城市和用户起点所在区域搜索，再通过每个候选的真实坐标查询步行路线；不把全市同名地点直接作为“附近”推荐。
- 提取并暂存 POI ID、名称、地址、坐标、类别及工具确实提供的其他相关字段。按 POI ID 去重；没有 ID 时结合名称、地址和坐标去重。同名的不同分店应保留各自身份。
- 排除类别明显不符、城市明显不符及用户明确排除的地点。不要将商业综合体误当其内部的咖啡馆，也不要把某分店的地址或坐标配给另一分店。
- 关键坐标缺失时，若环境提供 POI 详情能力，可按已返回的 ID 补查；仍无可靠坐标则跳过。地址缺失可补查；确实未返回时保留“地址未返回”，不得自行补写街道门牌。

## 3. 查询每个候选的步行路线

对有希望入选的候选调用**步行路线规划**。每次 `origin` 均为同一个原始起点，`destination` 为该 POI 的真实坐标。独立请求可在环境允许时并行执行。

- 每个最终推荐都必须具有本次高德调用成功返回的有效步行路线、距离和耗时。地点搜索结果中的距离、距离测量接口、驾车／骑行路线、直线距离及模型经验均不能替代步行路线。
- 按返回 schema 读取完整路线的总距离、总耗时，确认单位后统一保存为米和秒；数值字符串需正确解析。不要误取单个路段、交通灯数量或其他字段。
- 若返回多条有效步行路线，在未指定其他路线偏好时选预计耗时最短的一条；距离和耗时必须来自同一条路线，不能拼接不同方案的数据。
- 区分合法的零距离／零耗时与空值：只有工具明确返回起终点重合的有效路线时才接受零值；空路径、缺失耗时、负数或无法解析的数据视为不可验证。
- 保留“POI → 目的地坐标 → 所选路线 → 原始距离和耗时”的对应关系，用于筛选和最终回答。无需导出日志或额外 JSON。

## 4. 筛选、补查与排序

先检查硬条件，再排序，最后截取目标数量。

1. 时间判断使用**未舍入的原始秒数**。不超过 15 分钟即 `duration_seconds <= 900`；901 秒不能因显示为约 15 分钟而入选。若还有明确距离上限，同样使用实际步行路线总距离判断。
2. 其他硬条件只能由可靠返回字段确认。无法验证的硬条件不宣称满足；若因此不能给出符合条件的结果，说明具体缺失信息。对“安静一点”等软偏好，仍可按已验证条件推荐，但必须注明该偏好“未核实”。
3. 用户要求“优先近一点／距离最近”时按**步行距离升序**，同距离时按耗时升序；要求“最快／少走时间”时按耗时升序，再按距离升序。没有指定排序时，按步行耗时、距离升序。不能用搜索接口顺序代替路线排序。
4. 若偏好含多个维度，先满足明确的排序优先级，再用可验证字段比较；无法验证的偏好不作为已满足条件或虚构的排序依据。
5. 对首轮候选完成必要路线核验后再选优。不得仅因前几个已凑够数量，就忽略同批中更近或更符合明确偏好的候选。
6. 合格数量不足时，可针对缺口补查一轮：换等价类别词、翻页或适当扩大半径，并对新候选去重及查询步行路线。不得放宽用户的硬条件、改变起点或把超时地点混入合格列表。

搜索不穷尽整座城市，不无限翻页或重试。最终称“本次查询中优先推荐”，除非工具证据足够，不声称是全区域绝对最近、最好或唯一选择。

## 5. 生成回答

用用户的语言，先用一句话说明起点、关键限制及排序依据，再用表格或列表给出最多 3 个合格备选。每个地点必须包含：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 高德返回的准确名称，保留分店标识 | 高德返回的地址，缺失则注明 | 所选路线总距离 | 同一路线总耗时 | 一句与类型、路线或已验证偏好有关的理由 |

上表是字段模板，实际回答中全部替换为本次查询数据；没有合格地点时不填示例行。

- 距离可用整数米或适当精度的千米，不改变数量级；时间优先写“约 X 分 Y 秒”，整数分钟可直接写“约 X 分钟”。如用整分钟展示则向上取整，硬限制判断仍以原始秒数为准。
- 推荐理由使用已核验事实，例如“咖啡馆，符合类型要求；本次候选中步行距离最短”。不要仅凭名字推断环境、品质、座位、价格、景色或是否适合办公。
- 安静程度、排队情况、营业状态等若没有可靠依据，相关描述应标注“未核实”。不将“高德有收录”解释为“正在营业”，不将未返回的评分、价格或评论当事实。
- 有结果但不足数量时，说明“本次查询中仅核实到 N 个符合条件的地点”，简述是时间限制、候选不足还是部分路线查询失败。不要笼统断言当地不存在其他合适地点。
- 零结果时，说明本次查询未找到可确认满足条件的地点，并给出一项具体的可选调整，例如增加步行上限或扩大地点类型；等待用户接受后才按新条件查询。不附带不符合条件的“推荐”充数。
- 路线数据是预计值；无需输出逐路段导航、工具调用过程、评分规则、日志或与任务无关的长篇说明。

## 6. 工具异常

超时或临时服务错误可对失败请求重试一次；明确参数错误先按 schema 修正，不重复发送相同的无效请求。鉴权失败、配额不足或能力不可用时说明服务问题，不索取或暴露密钥。

- 地点搜索失败：说明“高德地点查询未成功，暂时无法提供已核实推荐”，不能用模型记忆补地点。
- 个别路线失败：跳过该地点，继续核验其他候选；如有合格结果则正常返回，并在影响数量时简短说明。
- 所有路线失败或都缺少有效耗时：说明“已查到候选地点，但未能取得有效步行路线，暂时无法确认步行可达推荐”。这与“没有符合条件的地点”不同。
- 无有效路线、未验证和超时的候选均不得出现在符合条件的推荐表中。

发送前核对：推荐数量、POI 身份、地址、同一起点、步行路线类型、距离耗时配对、未舍入时间限制、偏好排序和每句理由的依据。

工具能力参考：[高德 MCP Server 官方说明](https://developer.amap.com/api/mcp-server/summary)。具体调用以平台实际 schema 为准。
