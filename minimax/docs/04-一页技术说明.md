# 一页技术说明

## 定位

一个面向软件持续演进的 **SDD 上下文管理系统**：把「规格 → 代码 → 测试 → 任务状态」放进一个可检索、
可持久、可复用的上下文里，让开发助手（MiniMax）在正确的上下文上完成一次真实修改，并把结果验证、
进度与状态沉淀下来。

## 模块结构

| 文件 | 职责 |
| --- | --- |
| `sdd_context/config.py` | 环境变量 → `Settings`（工作区、状态目录、证据目录、数据库种类、MiniMax 接入参数、检索上限） |
| `sdd_context/workspace.py` | 扫描业务工程：规格条目（`spec/*.md`）、代码符号（`src/**/*.py` 的 AST）、测试用例（`tests/**/*.py`）、完整文件 |
| `sdd_context/corpus.py` | seekdb 语料层：`sdd_spec` / `sdd_code_symbol` / `sdd_test_case` / `sdd_document` 四张表 + `sdd_query_log` 查询日志；全文检索与 LIKE 回退 |
| `sdd_context/selection.py` | 上下文选择：任务 → 检索词 → 规格 / 符号 / 测试候选 → 规格↔符号↔测试链接 → 去重排序 |
| `sdd_context/context_pack.py` | 把选择结果渲染成带来源清单的 Markdown 上下文，并按字节预算截断 |
| `sdd_context/minimax_client.py` | MiniMax HTTP 客户端（Anthropic Messages / OpenAI Chat Completions 两种协议），保存请求与响应原文 |
| `sdd_context/patcher.py` | 解析模型回答里的 `FILE:` 块，校验路径不越界，写入工作区并生成 unified diff |
| `sdd_context/state.py` | 通过 PowerContext 读写任务状态（Source JSON + Work Contract / Task Outcome） |
| `sdd_context/cli.py` | 命令行入口（`import` / `context` / `plan` / `test` / `state` / `resume` / `queries` / `snapshot` / `reset` / `demo`） |

## 数据流

```
业务工程 workspace/
   │  import（扫描：规格 / 符号 / 测试 / 完整文件）
   ▼
seekdb 语料表 sdd_*  ── 全文检索 ──►  选择引擎（规格↔符号↔测试链接）
   │                                        │
   │                                        ▼
   │                              开发上下文（Markdown + 来源清单）
   │                                        │
   │                                        ▼
   │                                    MiniMax API（产出修改）
   │                                        │
   │                                        ▼
   │                                 写回工作区 → pytest（失败则回灌反馈重试）
   │                                        │
   ▼                                        ▼
PowerContext（pc_* 表，Source + Work 记录） ◄── 任务状态保存
   │
   └──► 新进程 resume：读回状态并继续使用
```

## 上下文选择方式

1. **检索词生成**：任务描述里的英文标识符原样保留；中文词经一份通用的工程词汇表展开
   （过滤→filter、负责人→assignee、排序→sort、状态→status……），同时保留中文原词用于 LIKE 回退。
2. **语料检索**：对 `sdd_spec` / `sdd_code_symbol` / `sdd_test_case` 分别做
   `MATCH(content) AGAINST (... IN BOOLEAN MODE)` 全文检索；检索为空时退化为 `LIKE` 扫描。
   每次检索都写入 `sdd_query_log`（SQL、参数、行数、耗时），形成可核对的数据库使用记录。
3. **规格↔代码↔测试链接**：从命中的规格文本里解析被引用的符号（如 `` `TaskBoardService.list_tasks` ``），
   用它反查代码符号（`sdd_code_symbol.name`）与提到该符号的测试（`sdd_test_case.content`）。
   命中「待实现」状态的规格加权，因为它们正是待办需求。
4. **补齐完整文件**：模型要输出的是完整文件，所以对选中符号所在文件再取一次完整内容
   （`sdd_document`），上下文里同时给出「符号片段」与「文件全文」，避免模型重写无关部分。
5. **输出**：Markdown 分节（任务 / 规格 / 代码 / 测试 / 完整文件 / 任务状态 / 来源清单），
   附机器可读的来源清单（`kind`、`id`、`path`、`title`）与本次执行的数据库查询记录。

## 三项技术的分工

| 技术 | 在本作品中承担的作用 | 具体落点 |
| --- | --- | --- |
| **seekdb** | 存储工程资料与索引，并提供检索结果用于构造上下文 | 嵌入式实例（`pylibseekdb`），语料表 `sdd_spec` / `sdd_code_symbol` / `sdd_test_case` / `sdd_document`，检索用 `FULLTEXT` 索引；查询写入 `sdd_query_log` |
| **PowerContext** | 保存任务进展与验证结果，并在后续运行中读取、使用 | 进程内 `open_builtin_runtime`；任务状态以 JSON Source 写入并按位置读回；`WorkContract` / `TaskOutcome` 记录目标、范围、完成情况与检查结果，`continuity()` 给出工作连续性视图；工程资料同时以 Source 形式入库存档 |
| **MiniMax** | 参与本次任务的代码生成与修改 | 通过 HTTP API 调用（Anthropic Messages 或 OpenAI Chat Completions 协议），输入是本模块组装的开发上下文，输出是被解析为文件级修改的代码块；请求与响应原文留档为开发记录 |

## 关键设计取舍

- **同一个 seekdb 实例承载两侧数据**：PowerContext 的 `pc_*` 表与本模块的 `sdd_*` 语料表在同一个
  嵌入式数据库里，状态与语料不会出现「两套数据对不上」的问题。
- **模块只改写工作区内的文件**：模型回答里的路径先经 `patcher._safe_target` 校验，越界直接拒绝。
- **测试反馈驱动修复**：修改后立刻跑测试，未通过则把失败日志作为「反馈」回灌给 MiniMax 继续修，
  最多 `SDD_MAX_ROUNDS` 轮；每轮的补丁与日志都单独留档。
- **状态用两种机制冗余保存**：JSON Source 便于程序化读回，Work Contract / Task Outcome 便于
  人工按时间线审阅；两者都在 PowerContext 里，重启后仍在。
- **不依赖 PowerContext 的原生代码索引**：该功能依赖 POSIX 文件锁，Windows 不可用；
  本模块改用标准库 `ast` 抽取符号，跨平台可用。
